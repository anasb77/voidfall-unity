# VoidFall Hybrid Assets and UI Design

> Date: 2026-08-20
> Status: approved direction; implementation pending plan
> Scope: active Unity project only; `voidfall.io` remains deprecated

## Problem

VoidFall performs deterministic content-authoring work while the player is trying to show its first frame:

- `EnsureArenaPlateViewport` synchronously generates the current arena and, on the menu, the Void arena.
- Each 1080p high-quality plate is about 2.23 million pixels. A non-Void save can generate two base textures and two equally sized detail textures before the menu is usable.
- Runtime-created textures remain CPU-readable and duplicate memory on the CPU and GPU.
- Every uGUI view is constructed through C# during `UIManager.Build`.
- The shared vertical-layout helper ignores child preferred heights, collapsing Settings and other stacked screens.
- Because the hierarchy exists only after Play Mode starts, layout mistakes are difficult to inspect and regression-test.

These are ownership and lifecycle problems. A loading screen, smaller textures, or a longer warm-up would only hide them.

## Goals

1. Remove procedural arena pixel generation from player startup and normal gameplay.
2. Make stable UI structure visible and editable as Unity prefab assets.
3. Separate UI structure from runtime state/event binding.
4. Preserve existing gameplay rules, save data, visuals, and deterministic simulation.
5. Add repository-owned regression gates for startup and the two confirmed UI failures.
6. Migrate incrementally so each phase can be compiled, captured, and rolled back independently.

## Non-goals

- No gameplay or balance rewrite.
- No URP migration, Addressables adoption, dependency-injection framework, or ECS conversion.
- No update to deprecated `voidfall.io`.
- No full TextMeshPro/font migration in the first phase.
- No immediate deletion of all legacy IMGUI code; removal follows behavior coverage.
- No runtime cache/versioning system for deterministic arena artwork.

## Decision

Use a hybrid Unity architecture:

- Deterministic visual content is generated by an Editor-only pipeline and shipped as normal Unity assets.
- Stable menu hierarchies are stored as uGUI prefabs.
- C# presenters/controllers bind game state and callbacks to those prefabs.
- Dynamic gameplay state, simulation, effects, and rules remain runtime code.

Web analogy:

```text
Editor-baked Texture/Sprite  = generated static asset from the web build step
uGUI prefab                  = saved component/DOM hierarchy
View MonoBehaviour           = component refs and display API
Presenter/controller         = state, event handlers, and service calls
```

## Architecture

### 1. Editor arena baker

Add an Editor-only command:

```text
Tools > VoidFall > Generate Arena Plates
```

The command reuses the existing deterministic `ArenaPlateFactory` pixel algorithms. It generates base and detail images for all three arenas and all three quality detail levels.

Generated source assets live under a deliberately narrow Resources subtree:

```text
Assets/VoidFall/Resources/VoidFall/Arenas/<quality>/<arena>/
```

Each generated pair is represented by an `ArenaPlateSet` ScriptableObject containing:

- `ArenaId`
- quality detail level
- base Sprite
- detail Sprite
- generated width and height
- generator schema/version

Generation uses a canonical 1920x1080 viewport. The existing 1.6M pre-overscan pixel cap means this also covers the current maximum high-quality bake density. The first supported layout matrix remains 1280x720 and 1920x1080, matching the current Windows target. Wider aspect ratios use aspect-preserving cover/crop; they must not stretch the artwork.

Importer requirements:

- Sprite texture type
- bilinear filtering
- clamp wrapping
- mipmaps disabled, matching the current runtime textures
- `isReadable = false` in player builds
- no lossy compression until visual comparison approves a platform format

The generator must be deterministic and idempotent: unchanged inputs produce identical asset bytes and do not churn `.meta` files.

Resources is chosen here because the project has a small, fixed asset set and does not currently use Addressables. The provider uses a single explicit `Resources.LoadAsync<ArenaPlateSet>` key such as `VoidFall/Arenas/2/Void/ArenaPlateSet`; it never uses `Resources.LoadAll`. All variants ship in the player, but only requested sets are loaded.

After runtime parity is proven, pixel-generation-only code moves into an Editor assembly so the player cannot accidentally call it.

### 2. Runtime arena provider

Add a small `ArenaPlateProvider` with one responsibility: return the pre-generated plate set for an arena and quality detail.

Runtime behavior:

1. Show a lightweight existing gradient/solid fallback immediately.
2. Load the required pre-generated plate asynchronously.
3. Publish the base/detail Sprites on the Unity main thread.
4. Preload the next arena during the existing six-second transition warning.
5. Keep only the active, menu, and next required sets resident; release obsolete loaded assets through one owner.

Missing/corrupt assets never trigger a synchronous runtime bake. Development builds log a precise error naming arena and quality; the player keeps the lightweight fallback.

`VoidFallGameRuntime` no longer owns:

- `_arenaPlatePrebakeTask`
- runtime Color32 bake buffers
- viewport-triggered plate invalidation/regeneration
- destruction of dynamically created arena textures

The quality setting selects a pre-generated quality variant. Window-size changes only rescale/crop the SpriteRenderer; they never regenerate pixels.

### 3. Prefab-based UI boundary

Create prefab assets for the stable retained UI:

```text
Assets/VoidFall/Resources/VoidFall/UI/VoidFallUIRoot.prefab
Assets/VoidFall/Resources/VoidFall/UI/Screens/MainMenu.prefab
Assets/VoidFall/Resources/VoidFall/UI/Screens/Settings.prefab
```

The first migration covers Main Menu and Settings because they contain both confirmed layout defects. Other screens continue working through their existing path until migrated one by one.

Each prefab owns:

- RectTransform hierarchy
- layout groups and layout elements
- visual Images and labels
- CanvasGroup/screen root
- serialized component references

Each view MonoBehaviour owns only:

- serialized references to controls and labels
- `Bind`/`Unbind` of callbacks
- methods that display supplied state
- local visual state such as reset confirmation

The runtime/presenter owns:

- save/settings values
- navigation state
- gameplay commands
- persistence and error handling

No prefab contains gameplay services or persistent save state.

Migrated prefabs also reference an editor-generated `VoidFallUISkin` asset containing the reusable rounded panels, button states, shadows, glows, and simple icons currently produced by `UISprites`. The Editor generator reuses the current visual algorithms, but migrated screens do not create these textures in the player. Legacy dynamic OS fonts may still be assigned during binding in this phase; importing licensed font/TMP assets is a separate decision.

### 4. UI layout contract

The shared layout contract is corrected rather than compensated per screen:

- Vertical stacks control child height and honor each child's `LayoutElement.preferredHeight`.
- Stack children do not force-expand vertically unless explicitly requested.
- Main-menu status cells receive flexible width.
- Status dividers remain fixed at 1x24 pixels and never receive flexible width.
- The root keeps the current 1280x720 CanvasScaler reference behavior during this phase to avoid unrelated visual drift.
- Main Menu and Settings use one safe-area-aware content root, even though Windows 16:9 is the current validated target.

The prefab hierarchy is the source of truth. Runtime code must not rebuild these rows or overwrite their structural layout values.

### 5. Bootstrap and loading

`UIManager.Create` loads/instantiates `VoidFallUIRoot.prefab` from the explicit `VoidFall/UI/VoidFallUIRoot` Resources key, then binds the supplied `UICallbacks`. It must not construct every screen tree in Awake and must not call `Resources.LoadAll`.

During incremental migration:

- Main Menu and Settings come from prefabs.
- Existing non-migrated screens may be created lazily when first opened.
- The home screen and global mute control are the only menu controls required before first interaction.
- Secondary screens, generated audio variants, and unused visual helpers must not block the first menu frame.

This creates a stable boundary without requiring a single risky all-screen rewrite.

## Data flow

```text
VoidFallGameRuntime
  -> requests ArenaPlateSet(arena, quality)
  -> ArenaPlateProvider loads generated asset
  -> runtime assigns base/detail sprites

VoidFallGameRuntime
  -> creates UIManager with callbacks
  -> UIManager instantiates prefab root
  -> MainMenuView / SettingsView bind callbacks
  <- view sends user actions through callbacks
  <- presenter supplies save/settings/menu state
```

## Error handling

- Missing arena asset: log one structured error, retain lightweight fallback, continue running.
- Failed async load: clear pending state so a later request can retry; never block on `.Result`.
- Duplicate UIManager: preserve singleton protection and destroy only the duplicate instance.
- Missing serialized UI reference: fail initialization with a screen/control-specific error in Development/Editor builds; disable that screen rather than throwing every frame.
- Save/settings failure: retain the current transactional persistence behavior and existing user notice path.

## Migration phases

### Phase A — regression harness and immediate UI correctness

- Add repository-owned EditMode/PlayMode test assemblies.
- Add structural tests for vertical row ordering/heights and fixed status dividers.
- Correct the shared layout contract and status strip.
- Capture Main Menu and Settings at 1280x720 and 1920x1080.

This is not the final prefab migration, but it restores usability and creates the safety net required for it.

### Phase B — editor-baked arena assets

- Add Editor assembly, generator, generated assets, and `ArenaPlateSet`.
- Add `ArenaPlateProvider`.
- Replace runtime plate generation and remove the synchronous first-frame bake path.
- Validate memory, launch timing, all arenas, and quality changes.

### Phase C — Main Menu and Settings prefabs

- Author prefab root and the two screen prefabs.
- Split construction from callback/state binding.
- Make secondary screens lazy.
- Repeat layout and capture matrix.

### Phase D — controlled continuation

- Migrate Workshop, Records, overlays, and HUD only after the first two prefabs prove the pattern.
- Pre-bake the procedural gameplay sprite atlas only if profiling shows meaningful remaining startup/run-start cost.
- Remove dead IMGUI menu code after equivalent behavior has repository-owned coverage.

## Testing

### EditMode

- Arena generator covers every `ArenaId` and detail level.
- Generated assets have valid base/detail Sprites, expected schema, and non-zero dimensions.
- Provider key selection maps arena and quality deterministically.
- Missing asset returns fallback/error state without invoking generation.
- Main-menu dividers have fixed width and no flexible width.
- Settings rows report and preserve preferred heights.

### PlayMode

- Boot reaches Main Menu without calling `BuildBasePixels` or `BuildDetailPixels`.
- Main Menu and Settings instantiate and bind callbacks from prefabs.
- Settings rows are ordered and non-overlapping after `Canvas.ForceUpdateCanvases`.
- Navigation Main Menu -> Settings -> Main Menu works with mouse and keyboard.
- Quality changes swap plate assets without a synchronous bake.
- Arena warning preloads and transition displays the next plate.

### Player validation

- Windows Development Build at 1280x720 and 1920x1080.
- Cold launch with a Void save and a non-Void save.
- Record time from post-splash player initialization to interactive Main Menu.
- Requirement: zero runtime arena-generation calls before interaction; target <=3 seconds on the audit machine, with profiler markers identifying any remaining cost.
- Memory Profiler confirms generated plate textures are not CPU-readable and obsolete variants are released.
- Main Menu and Settings captures show no overlap or expanded divider blocks.

## Acceptance criteria

1. No synchronous arena pixel generation occurs in a player build.
2. A non-Void save does not require both arenas to be generated before the menu appears.
3. Main Menu and Settings are prefab-backed and inspectable outside Play Mode.
4. Settings is usable at 1280x720; all rows remain non-overlapping and scroll when necessary.
5. Status dividers render at 1x24 pixels.
6. Current Core/Content/Persistence behavior and save schema remain unchanged.
7. Unity compilation, EditMode tests, PlayMode tests, and Windows player build pass from the repository.
8. Existing user working-tree changes remain preserved.

## Rollback

Each phase is isolated. If an asset or prefab phase fails validation, revert only that phase while retaining the tests. Generated assets are derived files with a documented generator command; their `.meta` files remain stable. No save migration or content-schema change is involved.
