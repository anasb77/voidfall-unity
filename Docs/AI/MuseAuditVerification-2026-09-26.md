## Additional findings worth keeping

**B001 — Curved projectile capacity is not restored by mass cleanup.** `TryInsertHostileShot` increments `CurvedShotCount`; ordinary expiry decrements it. `ClearTransitionProjectiles` disables shots and resets their order table without repairing that counter. Each live curved shot cleared this way consumes capacity for the rest of the run, eventually reaching the cap of 24. The next run resets it, so “permanently” and “after any transition all volleys fail” are overstatements. This weakens elite attacks rather than crashing or blocking progression. Treat it as a P2 gameplay defect. Inspect the Hydra/Null City mass-clear callers too; put counter/order/pool retirement under one consistent operation. [GameSim.cs:489](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Runtime/Gameplay/GameSim.cs:489), [Rift.cs:481](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Runtime/Gameplay/VoidFallGameRuntime.Rift.cs:481).

**B011 — Browser export/import is not a lossless Unity profile transfer.** The test starts with Dasher selected, Default/Dasher/Brute unlocked, three cleared void IDs, 1280×720, monitor 2 and bloom 0.7. After export/import: Default only, no cleared voids, automatic resolution/monitor and default bloom. The exporter and importer omit the corresponding fields. This does not affect ordinary native saves. The feature is explicitly labelled a *browser* export, so distinguish browser compatibility from a promised full Unity backup; nevertheless, a player round-tripping it loses these fields. Extend the transfer format compatibly or provide a clearly separate complete-profile backup, with field-coverage tests. [BrowserSaveExporter.cs:18](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Persistence/BrowserSaveExporter.cs:18), [BrowserSaveImporter.cs](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Persistence/BrowserSaveImporter.cs).

**B026 — An older executable rewrites a future profile schema.** `Load` sanitizes unknown versions down to 6, then immediately persists the result. The unknown field disappears from the primary file. The test verifies that the original survives in the rotating `.bak` initially, so this is not immediate irreversible destruction of every copy. A later save can rotate that recovery copy away. Reject or quarantine a future version without enabling ordinary writes over it; retain the original. This is a P2 downgrade/forward-compatibility risk, not evidence that current v6 profiles spontaneously corrupt. [SaveStore.cs:285](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Persistence/SaveStore.cs:285).

**B017 — The grid material instance lacks explicit cleanup ownership.** The test confirms that accessing `.material` in backdrop setup instantiates a material not registered in `_dynamicMaterials`. The normal setup has one `Awake` caller; the report did not establish repeated setup on every arena transition. Treat this as a small resource-lifecycle defect, not proven accumulating travel leakage. Register and destroy the instance, or use an appropriate property block. Do not blindly replace the color assignment with `sharedMaterial.color`: `DefaultUnlit` is shared with other rendering objects. [Arena.cs:194](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Runtime/Gameplay/VoidFallGameRuntime.Arena.cs:194), [runtime teardown:1305](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Runtime/Gameplay/VoidFallGameRuntime.cs:1305).

**B025 — Crascendo broad-phase queries deserve a dedicated optimization pass.** It unconditionally adds eight **cells**, not eight world units. A base radius-one query therefore becomes radius nine: up to 19×19 cells before occupied-bounds clipping. The controlled test populated 750 grid cells and issued 15,000 queries per setting. Radius one returned 128,480 candidates in 3.048 ms; radius nine returned 3,696,000 in 88.109 ms (about 28.8× candidates and 28.9× time in this sample). The enlarged radius exists to accommodate growing enemies. Simply removing it can miss collisions. Investigate a conservative bound based on active radii or a separate large-actor query, retaining order and golden-master behavior. These timings are a headless Editor microbenchmark on synthetic placement, **not** Crascendo frame times or a projected FPS improvement. [Crascendo.cs:20](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Runtime/Gameplay/VoidFallGameRuntime.Crascendo.cs:20), [GameSim.cs:243](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Runtime/Gameplay/GameSim.cs:243), [CollisionGrid.cs:96](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Core/CollisionGrid.cs:96).

**B020 — The canonical camera opts out of the pipeline's 2× MSAA.** The scene-specific test confirms this after the production post-processing override. The installed URP code checks both `camera.allowMSAA` and pipeline sample count. This is a valid configuration discrepancy to review. It does not prove that enabling MSAA fixes shader aliasing, that the chosen palette is washed out, or that bloom should be 0.7. HDR flags are a capability hierarchy; camera HDR true with pipeline HDR false results in HDR being unavailable, not two incompatible pipelines. Preserve the approved art and compare native captures and GPU cost before choosing changes. [SampleScene.unity:191](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/Scenes/SampleScene.unity:191), [VideoSettings.cs:43](C:/Users/AB/Desktop/voidfall-unity-main/voidfall-unity-main/Assets/VoidFall/Runtime/Gameplay/VoidFallGameRuntime.VideoSettings.cs:43).

## B024: separate the real edges from incorrect fixes

- **Real:** `EvaluateFormUnlocks` mutates the in-memory profile and announces the unlock while ignoring the persistence result. A write failure can therefore contradict its “crash cannot take the unlock back” comment. Its nested call during `SaveRun` is already reproduced in original F03.
- **Real source-level UI gaps:** Workshop `UIFocusTrigger` handles pointer enter/exit but not selection, so keyboard/controller selection does not invoke the same preview behavior. Dealer selects its first child button without filtering interactability. Controller cancel still closes the dealer, so “stuck forever” is not established.
- **Accessibility review:** cosmetic iframe blink uses `_ambientClock` even when reduced motion freezes cosmetic rotation. That is real code behavior; whether damage blinking should be replaced by steady damage feedback needs an explicit reduced-motion/flashing policy and a visual check.
- **Incorrect timer claim:** `_dealerCombatSeconds` advances inside `Simulate` after the `JourneyStopsCombat` early return. Rewards/Travel do not age it. Introduction-grace clocks likewise do not expire through safe-room wall time.
- **Incorrect reset conclusions:** `BeginDealerCrossing` assigns position/variation; opening assigns its frame guard; `HideJunction` deactivates the canvas that owns the room; `ResetLegendaries` sets beam lifetime to zero, and equip resets previous-player position. A cosmetic animation phase persisting across runs is not by itself a gameplay leak.
- **Incorrect width inference:** `MobilityTrailSpriteWidth=10` describes the sprite host; `MobilityTrailWidth=4` is the drawn line. The generator draws the four-unit gradient line and the runtime accounts for sprite bounds. Comparing the two constants alone cannot establish a 2.5× visible-width error. Changing 10 to 4 without checking sprite padding can introduce a new mismatch.
- **Intentional:** upper-side-only dealer appearances are the owner's approved revision. The preserved RareBoon ID, serialized currency keys, and legendary fragment fields are compatibility/data-model choices. Do not rename them as “cleanup.”

## Repair order suggested by the combined evidence

1. Fix the already reproduced profile transaction and crossing-flow defects (original F01–F03), then the new curved-shot retirement defect B001. Keep wallet ownership and route commit order explicit.
2. Add complete-profile transfer coverage and safe future-version handling (B011/B026), retaining recovery copies. Resolve B024 form-save error handling in the same transaction ownership design.
3. Profile dense Crascendo separately, alongside the existing enemy-update allocations and telemetry serialization costs. Use active-radius bounds without missing grown-enemy collisions. The microbenchmark is a reason to investigate, not permission to alter combat ordering.
4. Close material ownership, camera configuration and bake-freshness gaps. Verify the chosen render changes against native captures and the approved artwork.
5. Complete controller/focus and reduced-motion checks, then make pacing decisions from full-length playtests. Do not implement numerical balance/art suggestions merely because the submitted report labels them “Fix.”

The verification adds evidence and corrects the issue list. It does not certify a bug-free foundation or turn the untested hypotheses above into confirmed failures.
